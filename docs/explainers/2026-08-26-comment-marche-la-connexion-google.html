Le problème : le serveur ne peut croire personne

Aujourd'hui, quand tu rejoins une room, tu tapes un pseudo et le serveur te croit. C'est parfait pour un pseudo : si tu écris « Batman », personne n'est lésé.

Ça s'effondre dès qu'on veut un historique d'écoute. Le serveur doit retrouver tes morceaux, pas ceux d'un autre. S'il te croit sur parole, alors n'importe qui écrivant « je suis Léopold » lit ton historique. Le pseudo est une étiquette ; là il faut une preuve.

Fabriquer cette preuve soi-même, c'est stocker des mots de passe : les hacher correctement, gérer les fuites, les oublis, les réinitialisations par email. Beaucoup de travail, beaucoup de façons de se tromper, et une responsabilité qu'on ne veut pas.

L'idée d'OAuth. Déléguer la preuve à quelqu'un qui la détient déjà. Google sait qui tu es, tu y es déjà connecté. SyncMusic ne lui demande pas ton mot de passe : il lui demande de confirmer ton identité, d'une manière que SyncMusic puisse vérifier tout seul.

Les trois acteurs, et ce que chacun ignore

Tout le mécanisme s'éclaire quand on regarde qui sait quoi. C'est délibéré : chaque acteur en sait le moins possible.

ActeurCe qu'il saitCe qu'il ne saura jamais
Le navigateurtoi Il transporte les messages et garde les cookies. Le client_secret. Il ne voit jamais rien qui prouve à lui seul ton identité.
SyncMusicserveur Son client_id, son client_secret, et à la fin : ton identifiant Google, ton nom, ton email. Ton mot de passe Google. Il ne le voit à aucun moment, et ne peut donc pas le perdre.
Googletiers Qui tu es, et quelle application demande à te connaître. Ce que tu écoutes sur SyncMusic. Il confirme une identité, il ne suit pas l'usage.

Ce que tu as créé dans la console, champ par champ

Les cinq écrans que tu as remplis ne sont pas de l'administratif. Chaque champ répond à une question précise du protocole.

client_id

Le nom public de ton application auprès de Google. Il voyage dans l'URL, tout le monde peut le lire, et ça n'a aucune importance : il désigne l'app, il ne prouve rien.

client_secret

La preuve que c'est bien ton serveur qui parle. Il ne quitte jamais ton serveur, et c'est exactement ce qui rend ce flow sûr : le navigateur ne peut pas se faire passer pour l'app, parce qu'il n'a pas cette moitié-là.

Authorized redirect URIs

La liste blanche des adresses où Google accepte de te renvoyer après le consentement. Sans elle, un attaquant fabriquerait un lien de connexion à ton app en demandant à Google de renvoyer le résultat chez lui. Google compare au caractère près : un port qui change, un slash final en trop, et c'est redirect_uri_mismatch.

Scopes : openid, email, profile

Ce que l'app demande à savoir, et rien de plus. openid déclenche la délivrance d'un jeton d'identité ; les deux autres y ajoutent l'email et le nom d'affichage. Ce sont des scopes non sensibles : aucune validation Google à demander.

Test users

Tant que l'app est en mode « testing », Google ne laisse passer que les comptes de cette liste. C'est ce qui te permet de développer sans faire vérifier ton app. C'est aussi le piège numéro un : liste vide, ta propre connexion est refusée.

Le trajet complet

Étape par étape, avec le vrai code

  1. Le clic. Un simple lien vers /auth/login sur ton propre serveur. Aucun JavaScript Google dans la page.
  2. Le serveur prépare l'aller. Il tire deux valeurs au hasard, state et nonce, les range dans un cookie court, puis renvoie le navigateur chez Google : 
    // server/auth.ts
const state = token();
const nonce = token();
setCookie(response, names.oauth, `${state}.${nonce}`, {
  maxAgeSec: 600, secure: config.secure,
});

const target = new URL(GOOGLE.authorization);
target.searchParams.set("client_id", config.clientId);
target.searchParams.set("redirect_uri", redirectUri);
target.searchParams.set("response_type", "code");
target.searchParams.set("scope", "openid email profile");
target.searchParams.set("state", state);
target.searchParams.set("nonce", nonce);
  3. Le consentement. Là, tu es sur un domaine Google, avec le cadenas Google. C'est le seul endroit où ton mot de passe peut être tapé, et ce n'est pas notre page. C'est la propriété principale du système.
  4. Le retour. Google renvoie le navigateur vers ta redirect URI avec deux paramètres : un code, et le state que tu avais envoyé.
  5. Le code arrive sur ton serveur. Seul, il ne vaut rien. C'est un ticket à usage unique, valable quelques minutes, échangeable seulement par qui détient le secret.
  6. L'échange, hors du navigateur. Ton serveur appelle Google directement, en présentant le code et le client_secret. Cette requête ne traverse aucune machine que tu ne contrôles pas.
  7. Le jeton d'identité. Google répond un id_token : un JWT signé qui contient ton identifiant permanent (sub), ton email, ton nom.
  8. La vérification. Le point critique. Un JWT n'est pas chiffré : n'importe qui peut le lire, et n'importe qui peut en fabriquer un faux. Ce qui compte, c'est la signature. 
    // jose verifie la signature contre les cles publiques de Google,
// l emetteur, le destinataire et l expiration.
const { payload } = await jwtVerify(idToken, jwks, {
  issuer: [...GOOGLE.issuers],
  audience: config.clientId,
});
if (payload.nonce !== nonce) return failed();
  9. La session. Le serveur enregistre le compte, crée une session, pose un cookie, et te ramène à l'accueil connecté.
Pourquoi un code plutôt que le jeton directement ? Une variante ancienne d'OAuth renvoyait le jeton d'identité dans l'URL de retour. Le jeton passait alors par l'historique du navigateur, les logs des proxies, le header Referer. Le code d'autorisation corrige ça : ce qui transite par le navigateur est inutilisable seul, et ce qui est utilisable ne transite jamais par lui.

Les trois gardes, et l'attaque que chacun arrête

GardeCe qu'il faitL'attaque sans lui
state Une valeur au hasard, posée en cookie à l'aller, comparée au retour. Un attaquant t'envoie un lien de callback portant son code. Tu cliques, et ton navigateur se retrouve connecté à son compte. Tout ce que tu ajoutes ensuite atterrit chez lui.
nonce Une valeur au hasard envoyée à l'aller, que Google recopie dans le jeton. Un jeton d'identité valide, obtenu ailleurs pour une autre session, est rejoué ici. Le nonce lie le jeton à cette tentative de connexion précise.
La signature Vérifiée contre les clés publiques de Google, avec l'émetteur, le destinataire et l'expiration. Un JWT fabriqué de toutes pièces avec sub = ton identifiant. Sans vérification de signature, il passe.

Le cookie de state est à usage unique : il s'efface au début du callback, avant toute vérification. Sans ça, rejouer la même URL de retour rejouerait la connexion.

Après la connexion : la session

Le jeton Google a fait son travail et ne sert plus. Ce qui te garde connecté, c'est une session à nous.

Une session opaque, pas un JWT

On aurait pu signer un jeton et le poser en cookie. On a choisi un identifiant tiré au hasard, dont la base garde la trace. La raison tient en un mot : révocable. Se déconnecter supprime une ligne, et la session ne vaut plus rien dans la seconde. Un JWT signé, lui, reste valide jusqu'à son expiration, quoi qu'on fasse.

La base ne garde jamais le cookie

// server/db.ts — seule l empreinte est stockee
function fingerprint(rawId: string): string {
  return createHash("sha256").update(rawId).digest("hex");
}

Le navigateur détient la valeur en clair, la base son SHA-256. Une fuite du fichier .db, ou d'une vieille sauvegarde, ne livre aucune session utilisable : on ne remonte pas d'une empreinte à la valeur. Pas de sel ni d'algorithme lent ici, contrairement aux mots de passe : la valeur est déjà 128 bits tirés au hasard, il n'y a rien à deviner.

Les attributs du cookie, un par un

AttributPourquoi
HttpOnlyLe JavaScript de la page ne peut pas le lire. Une faille XSS ne donne pas la session.
SameSite=LaxPas Strict : le retour de Google est une navigation venue d'un autre site, et Strict ferait ignorer le cookie au callback. La connexion échouerait sans le moindre message.
Secure et __Host-Seulement en HTTPS. Safari refuse Secure sur http://localhost : en développement on retombe sur un nom simple, sinon le navigateur jette le cookie en silence.
Max-Age glissant60 jours, repoussés à chaque visite, mais jamais au-delà de 180 jours depuis la connexion. Le plafond dur borne ce qu'une session volée reste utilisable.

Ce qui casse en vrai

  1. redirect_uri_mismatch. L'adresse envoyée ne figure pas au caractère près dans la liste Google. Presque toujours un port ou un slash final. C'est aussi pourquoi BASE_URL est obligatoire et jamais déduite du header Host, qu'un client choisit librement.
  2. « Accès bloqué » au consentement. Ton compte n'est pas dans les test users. L'app est en mode testing, Google ne laisse passer personne d'autre.
  3. La connexion tourne en rond, sans erreur. Le symptôme d'un cookie jeté : SameSite=Strict, ou Secure posé sur du HTTP. Le navigateur ne signale rien, le serveur voit juste un cookie manquant.
  4. BASE_URL pointe au mauvais endroit. Sous npm run dev, l'app vit sur le port 5173 et Vite renvoie /auth vers 8787 : BASE_URL doit être http://localhost:5173, l'adresse que le navigateur affiche vraiment. Sous npm run serve, c'est 8787.
Sans identifiants Google, rien ne casse. Si les deux variables sont absentes, les routes de connexion répondent 404 et l'application reste entièrement utilisable en invité. C'est un mode de fonctionnement normal, pas une panne : un ami de passage ou un recruteur qui teste ne rencontre aucune étape nouvelle.

Comment tout ça se teste sans réseau

Aucun test n'appelle Google. On génère une paire de clés, on publie la moitié publique dans un JWKS local, et on signe des jetons de test avec la privée. Le token endpoint est remplacé par une fonction qui rend ce qu'on veut.

L'intérêt n'est pas la vitesse : c'est que les cas d'échec deviennent provocables. On ne peut pas demander à Google un jeton expiré, un jeton signé avec la mauvaise clé, ou un jeton destiné à une autre application. En local, si :

// server/auth.test.ts
it("refuse un jeton signe par une autre cle", async () => {
  const b = await banc();
  const response = await connecter(b, (nonce) => idToken({ nonce, key: autreCle }));
  expect(response.headers.get("location")).toBe("/?auth=failed");
  expect((await b.get("/api/me")).status).toBe(401);
});

Où on en est, et ce que ça débloque

Le serveur sait maintenant qui tu es sur ses routes HTTP. Trois choses manquent encore :

U3 — l'identité sur le WebSocket

La room passe par une connexion WebSocket, ouverte avant toute requête HTTP. Il faut lire le cookie au moment de l'ouverture pour que ton nom de compte remplace le pseudo.

U4 — le bouton

Rien n'est encore visible : pas de bouton de connexion, pas d'écran de compte. Le flow marche, personne ne peut le déclencher depuis l'interface.

U5 et U6 — historique et playlists

La raison d'être de tout ça. Le compte n'est pas une fin : c'est ce qui permet à quelque chose de survivre à la fermeture d'une room.
